Trust and checks

Status vocabulary

Every model carries one of five classes: it leads the model’s registry status and Status row, and is the chip beside its verdict; the rest of the line names the checks and where the model falls short. The five: exact for implemented rules; replicates [source] on [checks]; partial replication of [source]; anchored to [source], not validated as a forecaster; calibrated, no outcome benchmark. No status line calls a model validated; where the word appears on a model page it is a negative, such as “not validated as a forecaster”. A status class grades the model; the six words on the comparison page (plausible, off and so on) grade one experiment.

How each model is graded →
Exact for implemented rules

The rules are code, checked rule by rule, so a household answer can be verified by hand. Exact for the rules as implemented, which does not show that every area of legislation is covered. PolicyEngine microsimulation is in this class.

PolicyEngine microsimulation validation →
Replicates [source] on [checks]

Our code reproduces a published model’s output within a stated error, on the checks named and no others. For FRB/US the check is solver against solver, not a test of the economics. FRB/US is in this class.

FRB/US validation →
Partial replication of [source]

Some published outputs are reproduced, or are statistically consistent within a stated error; others miss or cannot be checked, and the status names both. The BoE SVAR, US HANK and DEFINE-UK are in this class; for DEFINE-UK the scenarios are only design-gated.

The five classes →
Anchored to [source], not validated as a forecaster

The model is set up to reproduce a published forecast by construction, so matching it is not evidence; its free-running and policy checks are reported separately. The OBR emulator is in this class.

OBR emulator validation →
Calibrated; no outcome benchmark

Targets are met by construction and no external outcome has yet been run against the model, so there is no ground truth to test against. OG-UK is in this class.

OG-UK validation →
Published anchor

A published figure a model is set up to match, such as an imposed steady-state target. An imposed match is an anchor, not a replication or a validation.

How each model is graded →
By construction

A match that holds because the model was set up to produce it, for example by fixing adjustments so it reproduces a published path. It shows the copy is faithful, not that the model forecasts well.

OBR emulator validation →
Anchored and free-running

Anchored: the model's adjustment terms are held so its baseline follows a published forecast. Free-running: those terms are released and the model's own equations drive the path. The OBR emulator is reported both ways.

OBR emulator validation →
Deltas only

Results are read as differences from the model's own baseline, never as levels, because that baseline sits far from the outturns.

DEFINE-UK validation →
Add-factor

An adjustment term added to a model equation. Held at the values that make the model reproduce a published forecast, add-factors anchor it; a reform can also enter as one, as the household-income add-factor HHDI_ADDFACTOR does in the OBR emulator.

Score a reform →
Design-gated

Checked that each scenario switches on exactly the policy settings its published definition lists, because no published results exist to check the numbers against. It catches a wrongly built scenario, not a wrong magnitude.

DEFINE-UK validation →
Paper-anchored

Checked against a few figures quoted in the authors’ earlier papers rather than a full published results table. For DEFINE-UK these are two FMM-2023 figures: the peak GDP effect of green public investment and baseline 2030 emissions.

DEFINE-UK validation →
Frozen edge

A forecast run from data cut off at a fixed past quarter, then scored against the outturns that followed. One frozen origin gives a handful of scores; a rolling evaluation over many origins is the stronger test.

BoE SVAR frozen origin →
Noise floor

The smallest difference that numerical round-off alone can produce. Two implementations agreeing at the noise floor differ no more than the arithmetic does.

FRB/US validation →
Release-to-release gap

How far two releases of the Fed’s own pyfrbus, with the same model and baseline, disagree on the same shock. Our FRB/US is judged against that gap rather than a chosen tolerance.

FRB/US validation →
Benchmark, not a validation

A comparison with another institution's figure that was produced on a different basis, so agreement or disagreement is informative but does not prove either right. The site uses the word in two other senses, each named where it appears: a naive forecast to beat (the drifting random walk), and a published range a result is set beside (a plausibility band, not a test passed).

Forecasts

Outturn

The published official figure for a period, which a forecast is scored against once it exists.

The scored period →
Forecast round

One dated set of forecasts, committed to Git before the outturn exists so it cannot be revised after the fact.

The archive of every round →
Data vintage

A dated snapshot of the data as it was published on a given day. Snapshots are never edited, so any score can be reproduced from the data the model saw.

The data vintages →
Credible band

The range the model puts a given probability on, such as 68% or 90%, from its posterior distribution. A band that contains every outturn can still be too wide.

BoE SVAR validation →
Drifting random walk

A naive benchmark forecast: the last value carried forward plus the average past change. A model has forecast skill only if it beats benchmarks like this one.

BoE SVAR against benchmarks →
Forecast skill

Forecasting better than a naive benchmark, out of sample, after allowing for the number of tests run. Matching a published forecast is not skill.

BoE SVAR against benchmarks →

Models and joins

Microsimulation

Applying the tax and benefit rules, written as code, to individual households, one at a time or across a weighted survey of the population.

PolicyEngine microsimulation →
Static costing

The cost of a reform with no change in behaviour and no feedback through the wider economy.

Score a reform →
Macro feedback

The second-round effect of a reform once output, prices and incomes respond; the OBR emulator adds it to a UK static costing.

Score a reform →
Incidence

How a change is shared across households: who gains and who loses. The incidence tools lay a macro path onto households; they are experimental and are not reform scores.

A macro shock across households →
SVAR

Structural vector autoregression: a statistical model of several series together, with named shocks identified by sign and zero restrictions.

BoE SVAR →
HANK

Heterogeneous-agent New Keynesian model: households differ in wealth and income, so a shock can be traced through the whole distribution.

US HANK →
OLG

Overlapping-generations model: age cohorts choose work and saving over their lifetimes, and the economy is solved for its long-run steady state or the path to it.

OG-UK →
Steady state

The long-run position the model economy settles at once every adjustment has played out.

OG-UK →
Stock-flow consistent

A model in which every flow of money is recorded as someone's payment and someone else's receipt, and stocks of assets and debts follow from those flows. DEFINE-UK is an ecological version that adds the climate.

DEFINE-UK →
EFO

The OBR's Economic and Fiscal Outlook, the official UK forecast the OBR emulator is anchored to.

OBR emulator →

Using the models

MCP

Model Context Protocol: a standard way for an AI client such as Claude or ChatGPT to call tools on a server. The hosted server needs no account or API key.

Connect a client →
Job

A slow call run in the background: start_job returns an id, and get_job_result is polled until the result is ready.

Access, limits and cold starts →
Cold start

The first call to a container that has just started, which pays a one-off loading or estimation cost; later calls are fast.
